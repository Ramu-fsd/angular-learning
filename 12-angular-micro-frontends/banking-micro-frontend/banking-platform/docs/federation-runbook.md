# Native Federation integration runbook

## 1. Start and validate each app
Run each remote in its own terminal:

| App | Command | URL |
|---|---|---|
| Accounts | `ng serve --port 4201` | `http://localhost:4201` |
| Payments | `ng serve --port 4202` | `http://localhost:4202` |
| Customers | `ng serve --port 4203` | `http://localhost:4203` |
| Admin | `ng serve --port 4204` | `http://localhost:4204` |
| Fraud & Risk | `ng serve --port 4205` | `http://localhost:4205` |

Validate each app independently before integrating it.

## 2. Configure the host
Run the Native Federation add command in the host and select the dynamic host option. Keep the generated configuration and use the exact manifest file format expected by the installed package version.

Register the remote entry URLs generated by each remote. Conceptually, the local entries are served by ports `4201` through `4205`; do not guess the actual remote entry filename. Inspect the generated files in each remote and use that exact filename.

## 3. Expose remote features
For each remote, inspect its generated federation configuration to identify the exposed module/component. Add an exposed route or standalone component in the remote if the generated starter does not expose the desired feature. Use the same exposed module identifier in the host's remote-loading route.

## 4. Add host routes
Create host routes for:
- `/accounts`
- `/payments`
- `/customers`
- `/admin`
- `/fraud-risk`

Load each remote through the API and route pattern generated by the installed Native Federation version. Do not mix configuration snippets from different major versions.

## 5. Validate the integrated platform
- Host loads when all remotes are available.
- Each route resolves the correct remote.
- A remote failure produces a useful fallback instead of crashing the host.
- Browser refresh works on remote-backed routes.
- Shared dependencies and shared UI library versions are compatible.
- Authentication context is passed safely; authorization remains enforced by backend APIs.
